# V2 阶段 11 对抗盲测与控制变量实验记录

> 本文档严格沿用 [V1 调优迭代日志](iterations.md) 的控制变量原则与红线纪律（详见 `docs/v2_specs/00_V2总体规格.md` 第 6 节）：
> 1. **双集验证**：每次调优同时在回归基线 `base52`（52 题）与独立盲测集 `holdout`（39 题）上跑批比对，以 `eval_runs.batch_id` 隔离批次、`usable` 逐题人工核对（多实体对比题按“提问要求对比的几个方法/点均须准确答全”从严判 `usable`）。
> 2. **零回归红线**：
>    - 高分拒答陷阱（`near_miss_refusal`，13 题）拒答率必须保持 **100%（13/13）**，且不得误入跨项目歧义分支；
>    - `base52` 四项核心指标任一项不得下跌超过 **2 个百分点**；
>    - 触发任一红线立即回滚，并以负实验形式如实记录。

## 评测数据集与基线参数

- **独立库与基线代码**：`knowledge_qa_v2` 独立 MySQL 库（43 篇文档、183 条切片：`go-gin` 39 篇 179 条切片保持 V1 原样，`project-alpha` 1 篇 1 条，`project-beta` 3 篇 3 条，`shared` 0 条），默认检索与生成参数沿用阶段 8：`VectorWeight = 0.75`、`KeywordWeight = 0.25`、`KeywordNormFloor = 45.0`、`TopN = 5`、`refuseThreshold = 0.35`、`ambiguityCompetitionDiff = 0.08`。
- **`base52` 回归集（52 题，`question_id = 1..52`）**：40 道可作答题 + 12 道应拒答题，用于守住 V1 阶段 8 的 `100% / 100% / 100% / 100%` 回归基线。
- **`holdout` 对抗盲测集（39 题，`question_id = 53..91`）**：由 `scripts/seed_holdout.go` 构建与入库，拆分为四类：
  1. `paraphrase_correction`（11 题，`id=53..63`）：同义换词改写 / 反问否定前提纠正（全可作答）；
  2. `near_miss_refusal`（13 题，`id=64..76`）：高分拒答陷阱——复用语料真实 API 名但追问文档未写明的底层参数、默认目录或实现细节（全应拒答）；
  3. `cross_para_compare`（7 题，`id=77..83`）：跨段多实体方法对比（全可作答，其中 `id=77` 即第 25 题金标指向 `gin-route-params.md` 的 `:name` 路径参数段 `gold_chunk_id=42`）；
  4. `project_governance`（8 题，`id=84..91`）：绑定 `project-alpha`、`project-beta`、`go-gin` 的项目硬隔离、`v1/v2` 文档弃用规范对比及跨项目边界拒答（5 道可作答 + 3 道应拒答）。

## 逐轮实验分析与归档

### 1. 迭代 0：阶段 10 结束原样基线
- **归档快照**：`eval/v2_iter0_base52.json`（`run_id=53..104`）、`eval/v2_iter0_holdout.json`（`run_id=105..143`）。
- **现象与诊断**：
  1. `base52` 全绿守住 V1 阶段 8 基线：命中 `40/40 (100%)`、引用 `38/38 (100%)`、可用 `38/38 (100%)`、拒答 `12/12 (100%)`，仅存 2 条生成侧保守误拒（`q33 filepath.Join`、`q37 regexp.MustCompile`）。
  2. `holdout` 首跑直接暴露两个真实结构短板：

     - **生成侧（第 26 题 `q78` + 类 1 误拒）**：第 26 题仅回答 `sync.Mutex` / `Lock/Unlock` 与 `sync.Once` 用途，遗漏核心调用方法 `once.Do`，按严格多实体标准判为 `usable=false`；类 1 中 `q53`（`gin.Default` 不想带中间件改用什么）、`q63`（`context.Context` 能否放结构体字段）出现生成侧保守误拒。
  3. **高分陷阱与跨项目行为**：`#12~#24`（`q64..q76`）共 13 道高分陷阱全部稳定触发 `"文档中没有依据"`（100% 拒答），且无一误入跨项目 `ambiguous` 提示分支。

### 2. 实验 1：检索层多实体覆盖保底（`ApplyMultiEntityCoverage`）— **保留**
- **单一变量改动**：在 `retrieve/merge.go` 实现 `ApplyMultiEntityCoverage` 并在 `api/handler.go` 接在融合排序之后。使用 `extractIdentifiers` 自动提取问题中 2 个及以上技术标识符（含 `.`/`_`/`-`、大小写驼峰、`go test` 子命令等，零硬编码词表），利用当前候选中已计算出的高区分度关键词（IDF ≥ `ln(2)`）检查 Top 5 是否漏掉某个实体的全部高 IDF 切片；若候选 Top 6..15 中存在缺失实体的高 IDF 切片，则将该实体最高分切片保底提升至第 5 位。
- **归档快照**：`eval/v2_iter1_multientity_base52.json`（`run_id=144..195`）、`eval/v2_iter1_multientity_holdout.json`（`run_id=196..234`）。
- **实验结果**：
  - `base52` 无任何回退（保持 100%/100%/100%/100%）。
  - `holdout` 第 25 题（`q77`，`run_id=220`）成功把 `c.Param` 切片 `chunk_id=45`（`[29,31,17,30,45]`）保底提入 Top 5，`cross_para_compare` 误拒从 **1 降为 0**，第 25 题从误拒转变为完整答出 `c.Query` 与 `c.Param` 并标 `usable=true`（该题 `gold_chunk_id=42` 仍记录为未命中同组主标，实效已覆盖答案；`q54` 在本次出现 1 次 LLM 采样波动拒答）。
- **结论**：多实体保底机制在不损伤任何基线的前提下有效解决了“单实体高分挤占多实体对比槽位”的结构缺陷，**决定保留**。

### 3. 实验 2：Cross-Encoder 重排（DashScope `gte-rerank` / `gte-rerank-v2`）— **拒绝（负迁移触发 >2% 回滚红线）**
- **单一变量改动**：完成 `config/config.go` 与 `retrieve/rerank.go`（同时兼容标准 `/rerank` 与 DashScope `text-rerank` 协议，未配 `RERANK_BASE_URL` 时零开销跳过）。遵循确认口径 **方案 A**：保留原融合分 `Final` 供 `0.35` 拒答阈值和 `0.08` 跨项目歧义判定，仅用重排对候选 Top 15 重排取 Top 5。
- **实测接口记录**：
  - 使用当前 DashScope API Key（通过环境变量传入）实测 `https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank`：默认 `gte-rerank` 返回 HTTP `403 AccessDenied`，切换至 **`gte-rerank-v2`** 后接口正常返回重排分数与序位。
- **归档快照**：`eval/v2_iter2_rerank_base52.json`（`run_id=235..286`）、`eval/v2_iter2_rerank_holdout.json`（`run_id=287..325`）。
- **实验结果**：
  - 正向收益：`holdout` 检索命中率升至 **100.00% (23/23)**（`q77` 将 `gold_chunk_id=42` 排入前 5），可用率升至 **100.00% (20/20)**（`q78` 带出更完整上文并答全 `once.Do`）。
  - **触发红线退化**：`base52` `q_id=47`（`run_id=281`：“在 Gin 中怎么让多条路由或整个服务复用同一段前置处理逻辑？”）属于几乎无精确 API 关键词的语义改写题，纯融合 `Final` 原本将中间件切片 `gold_chunk_id=24` 排在 Top 5（`[48,50,27,47,24]`），但 `gte-rerank-v2` 过度偏好字面包含“多条路由 / 复用”的 `Group` 切片（`[47,43,50,48,49]`），把 `chunk_id=24` 挤出前 5，导致回答只谈路由组前缀而漏掉全局中间件 `r.Use()`（`hit=false, usable=false`）。
  - `base52` 命中率由 `100.00%` 跌至 **`97.50%` (-2.50%)**，可用率由 `100.00%` 跌至 **`97.37%` (-2.63%)**，两项均突破 **2 个百分点** 回滚红线。
- **结论**：在现有技术文档混合检索基线上，`gte-rerank-v2` 虽提升多实体字面匹配排序，但会对纯语义总结题造成明显负迁移；保留 `retrieve/rerank.go` 可插拔实现与单测，但默认 **不启用 Rerank**（未配 `RERANK_BASE_URL` 即跳过）。

### 4. 实验 3（3a 与 3b）：高置信拒答二次复核与独立事实验证器 — **回滚（高分陷阱拒答跌至 46.15%）**
- **设计假设**：当 Top 1 融合分 ≥ `0.55` 而首次生成输出 `"文档中没有依据"` 时（如 `q33`/`q37`/`q53`/`q63`），引入一次通用二次复核 + 句级引用校验 + 独立事实验证器（拦截“未提及即否定”外推），试图降低高分误拒而不伤害高分陷阱拒答。
- **实验 3a（保守复核，归档 `eval/v2_iter3_verifier_*.json`，`base52 run_id=326..377`，`holdout run_id=378..416`）**：
  - 使用中性通用复核提示，模型在已首次拒答的高分误拒题上几乎全部二次维持拒答，`base52` 与 `holdout` 指标与实验 1 **完全持平（0 增益）**。
- **实验 3b（宽松复核草稿 + 独立事实验证器，归档 `eval/v2_iter4_relaxed_*.json`，`base52 run_id=417..468`，`holdout run_id=469..507`）**：
  - 虽将 `base52` `q37` 与 `holdout` `q53`/`q54` 从误拒挽回，**但触发严重红线退化**：`holdout` `near_miss_refusal` 拒答率由 `100.00% (13/13)` 断崖跌至 **`46.15% (6/13)`**，总体拒答率跌至 **`56.25% (9/16)`**。
  - **根因定位**：宽松复核草稿在面对无依据的高分陷阱题时，输出诸如：
    `文档中没有依据。资料仅说明 gin.Default() 自带 Logger（记录请求日志）[1][2]，但未提及该 Logger 默认将访问日志写入任何本地磁盘路径。`
    由于该回答既包含 `"文档中没有依据"` 又带有 `[1][2]` 引用标记，`generate.IsRefusal()` 按阶段 4 强约束（拒答不得携带引用，否则判作非拒答）将其判定为 `refused=false`；而独立事实验证器判断“资料确实未提及某磁盘路径”符合原文事实而输出 `PASS`，最终把“解释性拒答”放行成了 7 道误答的高分陷阱题！
- **结论**：依据红线原则，**立即回滚实验 3 的全部线上调用与提示词改动**（恢复 `api/handler.go` 为 `GenerateAnswer`，移除 `generate/llm.go`、`generate/prompt.go` 与 `generate/verifier_test.go` 中的实验 3 代码），`iter4` 作为负实验留档且保持 `usable=null`。

- **`holdout` 最终结果**：命中率 **`95.65% (22/23)`**、引用准确率 **`100.00% (20/20)`**、答案可用率 **`100.00% (20/20)`**（第 25 题 `q77` 与第 26 题 `q78` 均准确答全所有对比方法与关键点，判 `usable=true`）、拒答正确率 **`100.00% (16/16)`**，其中 `near_miss_refusal` 达到 **`13/13 (100.00%)`** 且零误入 `ambiguous`，`project_governance` 达到命中 `5/5 (100%)`、可用 `5/5 (100%)`、拒答 `3/3 (100%)`。
