# V2 阶段 11 对抗盲测与控制变量实验记录

> 本文档严格沿用 [V1 调优迭代日志](iterations.md) 的控制变量原则与红线纪律（详见 `docs/v2_specs/00_V2总体规格.md` 第 6 节）：
> 1. **双集验证**：每次调优同时在回归基线 `base52`（52 题）与独立盲测集 `holdout`（39 题）上跑批比对，以 `eval_runs.batch_id` 隔离批次、`usable` 逐题人工核对（多实体对比题按“提问要求对比的几个方法/点均须准确答全”从严判 `usable`）。
> 2. **零回归红线**：
>    - 高分拒答陷阱（`near_miss_refusal`，13 题）拒答率必须保持 **100%（13/13）**，且不得误入跨项目歧义分支；
>    - `base52` 四项核心指标任一项不得下跌超过 **2 个百分点**；
>    - 触发任一红线立即回滚，并以负实验形式如实记录。

## 评测数据集与基线参数

- **独立库与基线代码**：`knowledge_qa_v2` 独立 MySQL 库（43 篇文档、183 条切片：`go-gin` 39 篇 179 条切片保持 V1 原样，`project-alpha` 1 篇 1 条，`project-beta` 3 篇 3 条，`shared` 0 条），默认检索参数沿用阶段 8：`VectorWeight = 0.75`、`KeywordWeight = 0.25`、`KeywordNormFloor = 45.0`、`TopN = 5`、`refuseThreshold = 0.35`、`ambiguityCompetitionDiff = 0.08`。
- **`base52` 回归集（52 题，`question_id = 1..52`）**：40 道可作答题 + 12 道应拒答题，用于守住 V1 阶段 8 的 `100% / 100% / 100% / 100%` 回归基线。
- **`holdout` 对抗盲测集（39 题，`question_id = 53..91`）**：由 `scripts/seed_holdout.go` 构建与入库，拆分为四类：
  1. `paraphrase_correction`（11 题，`id=53..63`）：同义换词改写 / 反问否定前提纠正（全可作答）；
  2. `near_miss_refusal`（13 题，`id=64..76`）：高分拒答陷阱——复用语料真实 API 名但追问文档未写明的底层参数、默认目录或实现细节（全应拒答）；
  3. `cross_para_compare`（7 题，`id=77..83`）：跨段多实体方法对比（全可作答，其中 `id=77` 即第 25 题金标指向 `gin-route-params.md` 的 `:name` 路径参数段 `gold_chunk_id=42`）；
  4. `project_governance`（8 题，`id=84..91`）：绑定 `project-alpha`、`project-beta`、`go-gin` 的项目硬隔离、`v1/v2` 文档弃用规范对比及跨项目边界拒答（5 道可作答 + 3 道应拒答）。

## 逐轮实验分析与归档

### 1. 迭代 0：阶段 10 结束原样基线
- **归档快照**：`eval/v2_iter0_base52.json`（`run_id=53..104`）、`eval/v2_iter0_holdout.json`（`run_id=105..143`）。
- **现象与诊断**：
  1. `base52` 全绿守住 V1 阶段 8 基线：命中 `40/40 (100%)`、引用 `38/38 (100%)`、可用 `38/38 (100%)`、拒答 `12/12 (100%)`，仅存 2 条生成侧保守误拒（`q33 filepath.Join`、`q37 regexp.MustCompile`）。
  2. `holdout` 首跑暴露两个真实结构短板：
     - **检索侧（第 25 题 `q77`，`cross_para_compare`）**：问 `c.Query` 与 `c.Param` 差异，Top 5 为 `[29, 31, 17, 30, 32]` 全被 `c.Query` 高分切片挤占，`c.Param` 片段（`gold_chunk_id=42` 等）未进前 5，导致系统误拒；
     - **生成侧（第 26 题 `q78` + 类 1 误拒）**：第 26 题遗漏核心调用方法 `once.Do` 判 `usable=false`；类 1 中 `q53`、`q63` 出现生成侧保守误拒。
  3. **高分陷阱与跨项目行为**：`#12~#24`（`q64..q76`）13 道高分陷阱全部返回 `"文档中没有依据"`（100% 拒答），且零误入跨项目 `ambiguous` 分支。

### 2. 实验 1：检索层多实体覆盖保底（`ApplyMultiEntityCoverage`）— **保留**
- **单一变量改动**：在 `retrieve/merge.go` 实现 `ApplyMultiEntityCoverage` 并在 `api/handler.go` 接在融合排序之后，利用高区分度标识符与 IDF 检查 Top 5 漏覆盖，并从 Top 6..15 将缺失实体的最高分切片保底提升至第 5 位。
- **归档快照**：`eval/v2_iter1_multientity_base52.json`（`run_id=144..195`）、`eval/v2_iter1_multientity_holdout.json`（`run_id=196..234`）。
- **结果与结论**：`base52` 无回退；`holdout` 第 25 题（`q77`，`run_id=220`）保底提入 `c.Param` 切片 `chunk_id=45`（`[29,31,17,30,45]`），`cross_para_compare` 误拒从 `1` 降至 `0` 并完整答出对比点，**保留**。

### 3. 实验 2：Cross-Encoder 重排（DashScope `gte-rerank` / `gte-rerank-v2`）— **拒绝（负迁移触发 >2% 回滚红线）**
- **单一变量改动**：完成 `config/config.go` 与 `retrieve/rerank.go`（同时支持标准 `/rerank` 与 DashScope `text-rerank` 协议，未配 `RERANK_BASE_URL` 跳过）。实测当前 Key 对 `gte-rerank` 返回 `403 AccessDenied`，切换至 `gte-rerank-v2` 跑通全量。
- **归档快照**：`eval/v2_iter2_rerank_base52.json`（`run_id=235..286`）、`eval/v2_iter2_rerank_holdout.json`（`run_id=287..325`）。
- **结果与结论**：虽将 `holdout` 推至 `23/23` 命中与 `20/20` 可用，但 `base52` `q_id=47`（`run_id=281`）因无精确 API 关键词，被 `gte-rerank-v2` 偏好字面 `"多条路由"` 的 `Group` 切片（`[47,43,50,48,49]`）挤掉中间件切片 `gold_chunk_id=24`，使 `base52` 命中率跌至 **`97.50%` (-2.50%)**、可用率跌至 **`97.37%` (-2.63%)**，突破 >2% 回滚红线，**关闭默认启用**。

### 4. 实验 3（3a 与 3b）：高置信拒答复核 + 事实验证器 — **回滚（陷阱拒答崩盘至 46.15%）**
- **归档快照**：`eval/v2_iter3_verifier_*.json`（3a 保守复核 0 增益）、`eval/v2_iter4_relaxed_*.json`（3b 负实验，`base52 run_id=417..468`，`holdout run_id=469..507`）。
- **结果与根因**：3b 宽松草稿输出 `"文档中没有依据。资料[1]仅说明..."`，因携带 `[1]` 使 `generate.IsRefusal()` 判 `refused=false` 且验证器放行，致 `near_miss_refusal` 拒答率暴跌至 **`46.15% (6/13)`**。依据红线立即完整回滚实验 3 的全部线上逻辑。

### 5. 实验 5 & 最终 G1：Quote-First 结构化 JSON 输出（`generate/prompt.go` & `generate/llm.go`）— **最终保留**
- **核心设计**：
  - 严格维持单轮 `user` 消息（`len(Messages) == 1`）及 V1/V2 切片原文前缀格式，有条件附带 `response_format={"type":"json_object"}` 与 `max_tokens=2048`（遇 400 或空白响应自动回退纯文本请求，纯文本响应无缝回退原有阶段 4 校验链路）。
  - 要求模型先在 `quotes` 逐字摘录资料原句，再独立给出 `decision`（`"answer"|"refuse"`）和自然语言 `answer`：
    - `decision=="refuse"` 一律强制返回 `RefuseAnswer`（彻底将解释文本与 `IsRefusal` 物理隔离）；
    - `decision=="answer"` 校验证据 `quotes` 非空、编号不越界且原文经空白/反引号归一化后确实存在于对应切片中，随后抽取纯自然语言 `answer` 走 `validateCitations` 与阶段 4 重试逻辑（绝不泄露 JSON 原文）。
- **收敛调优（`iter5` -> 最终 `v2_final`）**：
  - **初版 G1（`eval/v2_iter5_g1_*.json`，`base52 run_id=599..650`，`holdout run_id=651..689`）**：一举将 `base52`（`q33`、`q37`）与 `holdout`（`q53`、`q54`、`q63`）的所有可答题误拒从 `2` 和 `3` **双双清零至 `0`**！但 `holdout` `q66`（`run_id=664`：“`filepath.Join` 会自动校验磁盘上是否存在吗？”）输出 `"不会，filepath.Join 只负责拼接路径并自动处理平台分隔符，资料未说明它会校验目标路径在磁盘上是否存在 [1]。"`，使 `near_miss_refusal` 暂为 `12/13 (92.31%)`。
  - **收敛 Prompt 规则 2（通用否定条款边界）**：在 `BuildPrompt` 规则 2 中明确区分“书面明确否定/禁止”与“仅介绍常规用途”：*若要给出否定结论（不能/不会/不适合/不支持），`quotes` 中必须明确写有禁止、否定或排他条款；只要 `quotes` 仅描述常规用途而未明确肯定或否定该附加行为，严禁凭常识补全“不会”，也严禁出现“资料未说明/未提及……”式解释，必须 `decision="refuse"`*（全句不含任何特定 API 名或题目词）。
  - **最终验收（`eval/v2_final_base52.json` `run_id=781..832`，`eval/v2_final_holdout.json` `run_id=833..871`）**：
    - `base52`：命中 **`100.00% (40/40)`**、引用 **`100.00% (40/40)`**、可用 **`100.00% (40/40)`**、拒答 **`100.00% (12/12)`**、误拒 **`0`**；
    - `holdout`：命中 **`95.65% (22/23)`**、引用 **`100.00% (23/23)`**、可用 **`100.00% (23/23)`**、拒答 **`100.00% (16/16)`**、误拒 **`0`**，其中 `near_miss_refusal` 恢复并保持 **`13/13 (100.00%)`**、`paraphrase_correction` 误拒 **`3 -> 0`**（`11/11`）、`cross_para_compare` **`7/7` 可用**、`project_governance` **`100%`**。

### 6. 实验 6：R1（Top 25 `0.5*Final + 0.5*normR` 凸组合）+ 最终 G1（DashScope `gte-rerank-v2`）— **R1 代码保留，默认关闭 Rerank**
- **单一变量改动**：在 `retrieve/rerank.go` 将 Rerank 候选窗口扩至 `RerankCandidateLimit = 25`，不改动 `MergedChunk.Final` 原始值，采用本地凸组合分 `blend = 0.5*Final + 0.5*normR`（对 `maxR - minR <= 1e-6` 做窄分差与除零保护）排序后经 `ApplyMultiEntityCoverage` 输出 Top 5。
- **归档快照**：`eval/v2_iter6_r1g1_base52.json`（`run_id=872..923`）、`eval/v2_iter6_r1g1_holdout.json`（`run_id=924..962`）。
- **实验结果与结论**：
  - `holdout` 上全项达到 **100%**（命中 `23/23`、引用 `23/23`、拒答 `16/16`、`near_miss_refusal 13/13`、误拒 `0`）；
  - 但在 `base52` `q_id=47`（`run_id=918`）中，因 `gte-rerank-v2` 仍给字面匹配的 `gin-routing` 切片打出了压倒性的高重排分（同时原 `Final` 与 chunk `24` 相近），50/50 凸组合依然将 `gold_chunk_id=24` 挤出 Top 5（`[47,43,50,48,49]`），使 `base52` 命中率维持 `39/40 (97.50%, -2.50%)`，仍触及 `> 2%` 回滚红线。
  - **结论**：保留 `retrieve/rerank.go` 的 R1 凸组合实现作为可选环境变量扩展（供后续更换更优重排模型时启用），**当前交付默认不配置 `RERANK_BASE_URL`（零开销跳过重排）**。
