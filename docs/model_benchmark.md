# 主流国产大模型 RAG 生成端控制变量横评报告

为了让这套 Knowledge QA Harness 的模型选型与护栏设计有真实、可对比的实验依据，我在本地 **`v3` 生产链路** 与 `knowledge_qa_v3` 数据库上，对 **4 家主流国内厂商的 6 款代表性大模型** 开展了一次**完全控制检索输入与校验规则**的横向评测（覆盖全量 **91 题**：`base52` 52 题 + `holdout` 39 题对抗盲测）。

> [!NOTE]
> **候选探测说明**：测试前我同时探测了 `MiniMax/MiniMax-M3`，接口返回 `The product is not activated`（当前账户未开通该模型计费权限），因此未纳入对比；最终参测的 **6 款模型** 均完整跑通 91 题且 **`API Error = 0`**。

## 二、控制变量实验设计

为确保横评结果只反映“大模型本身在严格引用协议下的指令遵循、证据对齐与推理能力”，我锁定了以下全部外部变量：

1. **统一冻结检索输入（零检索漂移）**：使用生产库统一的 `text-embedding-v3` 与 `v3` 混合检索引擎，事先冻结 91 题的 Top-5 证据片段与阈值门控结果：
   - **Base52 基础集（52 题）**：40 题可答 + 12 题应拒答（检索 Hit Rate **100.00%**，其中 2 题因 Top-1 分数 `< 0.35` 在检索门控直接拒答，不调用 LLM）。
   - **Holdout 对抗盲测集（39 题）**：23 题可答 + 16 题应拒答（检索 Hit Rate **95.65%**，1 题在检索门控直接拒答，其余 38 题进入 LLM）。
   - **单模型 LLM 逻辑题量**：每款模型实测 `50 + 38 = 88` 题（对应 `63` 道可答题 + `25` 道进入生成的应拒答题，另有 `3` 道在检索阶段即被阈值拦截）。
2. **完全一致的生产 Prompt 与硬校验闭环**：统一调用 `generate.ChatClient.GenerateAnswer`（Quote-First 先摘录原文再作答、JSON 结构化输出、`response_format=json_object` 失败自动降级纯文本兜底、最多 1 次自动纠错重试；若两次仍未通过原文摘录或句级 `[n]` 引用校验，Harness 强制兜底拒答 `文档中没有依据`）。

## 六、核心工程发现、Bad Case 归因与已落地的代码优化

### 1. Harness 硬护栏证明了“宁可保守拒答、绝不放行未校验输出”
无论参测模型强弱，**幻觉放行率全部压制到 0（引用合规率 100.00%、拒答准确率 100.00%）**。模型差异没有变成“编造依据或丢失来源编号”，而是被 Harness 两级校验隔离成可量化的重试与拒答代价：
- **`qwen-max`（非思考版）**：共触发 **18 次自动重试**（106 次 HTTP 请求）。其中 **7 题在重试 1 次后纠偏通过**（`q#3`、`q#39`、`q#43`、`q#45`、`q#53`、`q#54`、`q#82`）；**10 题两次仍未通过 Quote-First / 句级校验 (`validation_failed=true`)** 而被 Harness 安全拦截拒答（集中在跨段对比或多问合一题，如 `q#79`、`q#81`、`q#83`、`q#4`、`q#9`、`q#26`、`q#27`、`q#30`、`q#40`、`q#47`）；仅 **`q#8`** 属于 `validation_failed=false` 的模型自身保守拒答。
- **`glm-5.3`**：整体推理速度快（P50 仅 `4.16s`，是思考旗舰里最快的），回答细节丰富（例如 `q#77` 会顺带补充文档片段里的示例 URL `/search?q=gin&page=2`），但格式稳定性略逊于 `qwen3.8-max` 与 `kimi-k3.1-pro`，触发 4 次重试（`q#4`、`q#29` 重试恢复），`q#9` 与 `q#82` 两次校验失败被拦截。
- **`kimi-k3.1-pro`**：仅在 `q#9` 触发 1 次重试并成功恢复，最终 **63/63 全过**，且跨段信息整合最完整（如 `q#77` 主动带出 `[5]` 中“路径参数没有类型系统、需要自行校验与转换”的边界细节；`q#81` 完整融合 `[1][2][3]` 解释 `embed` 单文件部署收益）。

### 2. 从 `deepseek-v4-pro` `q#81` 挖出的真实边界 Bug —— 并已合入代码优化
在测试期间，`deepseek-v4-pro` 在 `holdout q#81`（比较 `r.Static`、`r.StaticFS`、`r.StaticFile`）单题耗时 **`103,274 ms`**（`httpReqs=3`、`retried=true`、`json_fallback=1`，3 次请求累计 `completion_tokens=4,532`、其中 `reasoning_tokens=4,095`），虽然依靠内置兜底最终给出了满分带引用回答，但直接原因非常清晰：
- DashScope 对思考模型会将 `reasoning_tokens` 计入 `max_tokens` 配额，而此前 [generate/llm.go](../generate/llm.go) 默认将结构化模式 `jsonModeMaxTokens` 统一设为 `2048`，导致思考过程耗尽预算后返回空 `content`，触发“降级纯文本 + 重试”的额外开销。
- **已在主干合入的工程修复（见 [generate/llm.go](../generate/llm.go) 与 [generate/prompt_v2_test.go](../generate/prompt_v2_test.go)）**：
  1. 新增 `isLikelyReasoningModel` 与 `jsonModeMaxTokensForModel`：对非思考模型保持 `2048` 紧配额，对已知思考模型家族（`deepseek-r1` / `deepseek-reasoner` / `deepseek-v4` / `qwen3` / `qwq` / `glm-5` / `kimi-k3` / `o1` / `o3` / `o4` 等）自动将结构化 `max_tokens` 提升至 **`4096`**，并支持通过可选环境变量 `LLM_JSON_MAX_TOKENS` 显式覆盖。
  2. 在 `chatOnceMeta` 与 `chatJSON` 中补充 `finish_reason="length"` 与 `reasoning_content` 截断诊断日志，触发空正文降级时可一目了然地定位“思考配额耗尽”。
  3. 已在 `TestJSONModeMaxTokensAdaptiveForReasoningModels` 完成完整单元测试覆盖（包含非思考/思考模型默认配额、环境变量覆盖与异常值回退、`finish_reason="length"` 截断降级闭环）。

### 3. 成本与延迟的剪刀差结论
- **`deepseek-chat`** 以 **837.4 ms** 全量加权均延、**6,944** total completion tokens、**0 次重试** 拿到 **100% 全维度满分**；而同样拿满分的三大思考旗舰（`deepseek-v4-pro`、`qwen3.8-max`、`kimi-k3.1-pro`）全量平均耗时 **9.4s ~ 13.3s**（慢 **11 ~ 16 倍**），生成侧 token 消耗高 **4.4 ~ 7.3 倍**（计入 `glm-5.3` 则高至 **7.6 倍**）。
- 说明在**精确切块召回 + Harness Quote-First 硬约束明确**的知识库问答场景下，指令遵循稳定的轻快非思考模型完全足够跑满效果上限，无需盲目用高延迟思考模型承担线上高频流量。

## 七、分场景模型选型建议

| 业务场景 | 推荐首选 | 备选方案 | 核心理由 |
